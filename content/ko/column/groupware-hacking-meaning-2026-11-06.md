그룹웨어가 해킹당했다는 소식을 들으면 우리는 무엇부터 걱정할까?

직원의 이름과 연락처, 전자결재 문서, 업무 파일의 유출을 먼저 떠올릴 것이다. 물론 모두 중요하다.

하지만 그보다 더 깊이 살펴야 할 문제가 있다.

회사에서는 업무를 처리하면서 이런 대화를 주고받는다.

> "AWS 접속 계정은 이 문서에 있습니다."  
> "Google Cloud 서비스 계정 키는 첨부파일을 확인해 주세요."  
> "NAVER Cloud 관리자 계정과 내부 서버 접속 정보는 운영 매뉴얼에 정리했습니다."  
> "VPN과 데이터베이스 접속 비밀번호는 지난번에 공유한 내용과 같습니다."

*위 문장은 이해를 돕기 위한 가상의 예시다.*

우리는 이런 기록을 편리한 업무 공유라고 생각한다. 공격자에게는 다르게 보일 수 있다.

**그룹웨어 어딘가에 남겨진 ID와 비밀번호, API 키, 인증 토큰은 다른 시스템으로 들어갈 수 있는 열쇠가 될 수 있기 때문이다.**

> **그룹웨어 해킹의 의미는 그룹웨어 하나가 뚫렸다는 데서 끝나지 않는다.**  
> **그 안에 기록된 접속 정보가 여전히 유효하다면, 다음 공격 대상은 AWS·Google Cloud·NAVER Cloud, 그리고 내부 온프레미스 시스템이 될 수 있다.**

---

## 먼저 결론부터: 그룹웨어는 회사 시스템의 '접속 지도'가 될 수 있다

그룹웨어는 단순한 메신저가 아니다.

프로젝트 대화, 서버 운영 절차, 장애 처리 기록, 협력사 계정, 첨부파일, 인수인계 문서가 쌓인다. 경우에 따라 이 기록에는 **실제 접속 주소와 자격증명(Credentials)**까지 포함된다.

공격자가 이러한 자료에 접근할 수 있었다면, 침해 범위를 그룹웨어의 사용자 정보로만 평가해서는 안 된다.

확인해야 할 질문은 세 가지다.

- **그룹웨어에 어떤 외부·내부 시스템의 접속 정보가 기록돼 있는가?**
- **그 접속 정보 중 지금도 사용할 수 있는 비밀번호·API 키·토큰이 있는가?**
- **그 자격증명으로 실제 다른 시스템에 접근한 흔적은 없는가?**

이것이 지금 그룹웨어 해킹을 바라보는 사이버보안의 출발점이다.

> **기업 업무시스템에서 외부 접근이 발생했을 때, 그곳에 저장된 '다른 시스템으로 가는 열쇠'까지 확인하고 있는가?**

## 2. 공격자가 그룹웨어에서 정말 노릴 수 있는 것은 무엇인가

그룹웨어의 대화와 문서에는 일상적인 업무 과정에서 다음과 같은 정보가 남을 수 있다.

| No. | 기록될 수 있는 정보 | 그 정보가 유출됐을 때의 위험 |
| ---: | --- | --- |
| 1 | **AWS** 콘솔 계정, IAM 액세스 키 | 권한 범위에 따라 클라우드 자원 조회·변경, 데이터 접근 가능 |
| 2 | **Google Cloud** 계정, 서비스 계정 키 | 서비스 계정 권한으로 API 호출, 저장소·인프라 접근 가능 |
| 3 | **NAVER Cloud** 계정, API 인증키 | 부여된 권한 범위 안에서 클라우드 자원 접근·조작 가능 |
| 4 | **내부 온프레미스** 서버 계정, SSH 키, 관리자 비밀번호 | VPN·원격접속 등 도달 가능한 경로가 있으면 내부 서버 침입 시도 가능 |
| 5 | **VPN·SSO·관리자 포털** 접속 정보 | 외부와 내부를 연결하는 인증 경로의 공격 가능성 확대 |
| 6 | **DB·백업·CI/CD** 계정, 토큰, 복구 정보 | 데이터 접근, 배포 과정 변조, 백업 훼손 등으로 피해 확대 가능 |

가령 운영 담당자가 장애 대응을 위해 서버 주소와 계정을 채팅으로 보내거나, 개발자가 테스트용 API 키를 작업 문서에 붙여 넣을 수 있다. 몇 년 전에 공유한 관리자 비밀번호가 이후에도 바뀌지 않았다면 당시의 기록은 오늘도 유효할 수 있다.

특히 **클라우드 API 키나 서비스 계정 키는 사람의 로그인 화면을 거치지 않고 사용되는 경우가 있다.** 이러한 자격증명이 유출됐다면 그룹웨어 로그인에 2차 인증을 추가하더라도 해당 키가 자동으로 무효화되지는 않는다.

AWS는 장기 액세스 키보다 임시 자격증명을 권장하고, Google Cloud도 서비스 계정 키의 외부 유출이 실제 클라우드 접근으로 이어질 수 있다고 경고한다. [AWS IAM 모범 사례](https://aws.amazon.com/iam/resources/best-practices/) · [Google Cloud 서비스 계정 키 보안](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)

**접속 주소나 계정 이름만 유출됐다고 곧바로 침입이 성공하는 것은 아니다.** 하지만 유효한 비밀번호·키·토큰, 충분한 권한, 실제 네트워크 접근 경로가 함께 갖춰지면 위험은 급격히 커진다.

## 3. 비밀번호 유출 이후의 공격은 하나가 아니다

그룹웨어에서 자격증명이 노출됐다고 가정하면 공격은 여러 경로로 이어질 수 있다.

### 3-1. 유출된 비밀번호로 직접 로그인

메시지에 남아 있던 VPN, 관리자 포털, 내부 서버의 계정과 비밀번호가 여전히 유효하다면 공격자는 해당 시스템에 로그인하려 할 수 있다. 이는 **이미 확보한 자격증명의 악용**이다.

### 3-2. 다른 서비스에 같은 ID·비밀번호를 대입

그룹웨어나 다른 침해사고에서 확보한 ID·비밀번호 조합을 여러 로그인 서비스에 대입하는 공격이 **크리덴셜 스터핑(Credential Stuffing)**이다.

비밀번호 재사용이 있다면 메일, SaaS, 클라우드 콘솔 등으로 피해가 번질 수 있다. 다만 **모든 자격증명 악용이 크리덴셜 스터핑인 것은 아니다.** [OWASP 크리덴셜 스터핑 대응](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet)

### 3-3. API 키·토큰·서비스 계정으로 접근

사람이 입력하는 비밀번호와 별개로, 유출된 API 키나 서비스 계정 자격증명이 사용될 수 있다. 공격자는 해당 키에 부여된 권한 안에서 자원 조회·변경을 시도할 수 있다.

### 3-4. 내부 시스템으로 공격 확대

내부 서버가 인터넷에 노출돼 있지 않다면 외부에서 바로 접근하기는 어렵다. 그러나 **VPN·원격접속 계정이 탈취되거나 감염된 PC가 경유지로 이용되면** 내부 온프레미스 시스템도 공격 대상이 된다.

아래는 실제 사건의 경과가 아닌 **가상의 확산 시나리오**다.

```text
그룹웨어의 채팅·첨부파일·운영 문서에 무단 접근
                 ↓
외부 클라우드·VPN·내부 서버 접속 정보 확보
                 ↓
유효한 비밀번호·API 키·토큰 식별
                 ↓
AWS / Google Cloud / NAVER Cloud / VPN 등 접근 시도
                 ↓
인증 성공 또는 탈취한 권한 악용
                 ↓
데이터 접근 · 추가 자격증명 확보 · 내부 이동 시도
```

공격이 실제로 어디까지 진행되는지는 **유출된 정보의 종류, 유효기간, 접근권한, 추가 인증, 네트워크 통제**에 달려 있다. 그러나 이러한 연쇄 위험을 평가하지 않은 채 그룹웨어만 복구한다면 중요한 대응이 빠질 수 있다.

## 4. 2차 인증만으로는 해결되지 않는 이유

플로우의 새 기기 로그인 본인 인증 강화는 필요한 보안 조치다. 조직의 다른 SaaS와 관리자 계정에도 강력한 다중요소 인증(MFA)을 적용하는 것이 바람직하다.

하지만 그룹웨어의 2차 인증은 **그룹웨어 밖에 이미 저장·공유됐던 비밀번호와 API 키까지 보호해 주지는 않는다.**

이미 유출된 자격증명이 다른 시스템에서 그대로 사용 가능하다면, 그 시스템에서 별도로 폐기·교체해야 한다.

- 그룹웨어 비밀번호 변경만으로 **AWS 액세스 키**가 폐기되지는 않는다.
- 그룹웨어의 MFA만으로 **Google Cloud 서비스 계정 키**의 사용이 차단되지는 않는다.
- 그룹웨어에서 메시지를 삭제해도 **이미 복사된 내부 서버 비밀번호**는 유효할 수 있다.
- 사용자 계정의 비밀번호를 바꿔도 **탈취된 세션·토큰**이 그대로 남을 수 있어 별도 점검이 필요하다.

> **그룹웨어 계정을 지키는 것과, 그룹웨어에 기록된 다른 시스템의 접속 권한을 보호하는 것은 서로 다른 과제다.**

## 5. 지금 기업이 확인해야 할 것은 '무슨 정보가 있었는가'와 '어디에서 사용됐는가'이다

| No. | 우선 점검 항목 | 실행할 조치 |
| ---: | --- | --- |
| 1 | **그룹웨어 내부 자격증명** | 채팅·게시글·첨부파일·운영 매뉴얼에 남은 비밀번호, 키, 토큰의 존재 여부를 **승인된 관리자·보안 절차로** 조사. 원문을 별도 목록으로 수집하지 말 것 |
| 2 | **클라우드 계정·키** | AWS·Google Cloud·NAVER Cloud의 노출 의심 키를 우선 식별하고 **폐기·교체**, 관리자 계정과 권한 재점검 |
| 3 | **온프레미스 접속 정보** | VPN·SSO·AD·Linux/Windows 관리자·DB·백업 계정의 유효성, 비밀번호 재사용, 접근 경로 점검 |
| 4 | **인증 성공 여부** | 실패한 로그인뿐 아니라 **성공한 로그인, MFA 실패, 신규 기기, 비정상 위치·시간대** 확인 |
| 5 | **접근 이후의 행위** | 대량 다운로드, IAM 정책 변경, 신규 키 발급, 원격 명령 실행, 파일 변경, 외부 전송 조사 |
| 6 | **추가 침입 차단** | 의심 계정 일시 차단, 세션·토큰 무효화, 필요한 패치 적용, 권한 축소 및 네트워크 경로 제한 |
| 7 | **재발 방지** | 비밀번호 관리자·비밀정보 관리 체계(Secrets Manager) 활용, 평문 채팅 공유 금지, 최소 권한과 피싱 방어형 MFA 적용 |

여기서 중요한 것은 **비밀번호를 일괄 변경했다는 사실만으로 조사를 끝내지 않는 것**이다.

유출이 의심되는 키와 비밀번호는 신속히 폐기·교체해야 하지만, 동시에 **이미 사용된 흔적**을 확인해야 한다. AWS의 CloudTrail, Google Cloud의 Cloud Audit Logs, NAVER Cloud의 서비스별 활동·감사 로그, VPN·SSO·서버 인증 로그를 연결해 보는 이유다.

미국 CISA도 자격증명 노출 위험에 대한 지침에서 비밀번호 변경, 소스·설정에 포함된 비밀정보 점검, 인증 로그 모니터링, 피싱 방어형 MFA를 함께 권고한다. [CISA 자격증명 위험 대응 권고](https://content.govdelivery.com/accounts/USDHSCISA/bulletins/3dc471c)

## 6. 정보보안 점검을 넘어, 실제 계정 공격을 확인해야 한다

정보보안 관점의 점검에서는 다음과 같은 질문을 자주 한다.

- 그룹웨어에 2차 인증을 도입했는가?
- 접근권한 정책을 수립했는가?
- 비밀번호 변경과 보안 교육을 실시했는가?

모두 필요한 조치다.

그런데 사이버보안 대응에서는 질문이 달라져야 한다.

- **유출이 의심되는 계정으로 실제 로그인이 성공했는가?**
- **어떤 클라우드 자원과 내부 서버에 접근했는가?**
- **권한 변경, 프로세스 실행, 파일 접근, 데이터 외부 전송이 이어졌는가?**
- **공격이 진행 중이라면 지금 차단할 수 있는가?**

웹방화벽(WAF)은 자신을 통과하는 웹 요청을 분석하고 로그인 공격을 탐지·차단하는 데 기여할 수 있다. 그러나 **다른 기업이 운영하는 SaaS 내부의 인증 이벤트를 WAF만으로 모두 볼 수는 없다.** SaaS 감사 로그, SSO·VPN 로그, 클라우드 감사 로그, 서버·PC 행위 데이터를 확보해 연결해야 한다.

PLURA-XDR이 지향하는 통합 사이버보안도 이 지점에 있다. **웹·계정·서버·PC의 공격 증거를 가능한 범위에서 연결하고, AI가 그 맥락을 분석하도록 도우며, 보안 운영자가 신속히 차단·조치할 수 있는 체계**가 필요하다.

> **가시성은 AI의 눈이다.**  
> **AI에게 실제 인증·행위 데이터가 없다면, 클라우드와 온프레미스로 이어지는 공격의 맥락을 정확히 설명할 수 없다.**

AI의 분석은 확보된 로그와 증거를 바탕으로 검증해야 한다. 볼 수 없는 영역의 공격까지 탐지했다고 주장해서는 안 된다.

## 맺음말: 해커가 가져간 것은 '업무자료'만이 아닐 수 있다

그룹웨어의 침해사고를 단순히 메신저나 전자결재 시스템의 문제로 보면 안 된다.

그 안에는 **우리 회사가 어떤 클라우드를 사용하고, 어디에 서버가 있으며, 누가 어떤 권한을 갖고, 무엇으로 접속하는지**에 관한 정보가 쌓여 있을 수 있다.

특히 그 기록에 유효한 ID와 비밀번호, API 키, 인증 토큰이 남아 있었다면 공격자는 그룹웨어 밖의 시스템을 노릴 수 있다.

물론 **이번에 알려진 특정 사고에서 그러한 자격증명이 실제로 유출됐다는 뜻은 아니다.** 확인되지 않은 사실을 단정해서는 안 된다. 하지만 가능한 공격 경로를 지금 점검하고, 실제 사용 흔적을 찾는 일은 미룰 이유가 없다.

> **그룹웨어가 해킹당했다면, 그 안에 무엇이 있었는지 확인해야 한다.**
>
> **그 안에 다른 시스템의 열쇠가 있었다면, 그 열쇠가 지금도 열리는지 확인해야 한다.**
>
> **그리고 누군가 이미 그 열쇠를 사용했는지 찾아내야 한다.**

**그룹웨어 해킹이 의미하는 바를 이해한다는 것은, 해킹당한 서비스만 보는 것이 아니라 그 서비스에 연결된 기업 전체의 공격 위험을 보는 것이다.**
